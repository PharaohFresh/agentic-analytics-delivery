# Changelog

## 2026-10-31

- `delivery verify` now binds the whole parsed `approval.json`. The SHA-256 of its canonical JSON is recorded in the first journal record and in the receipt, and verify checks the retained approval against both. Before this, only the approval's plan hash and approver were checked, so editing another field such as `authorization_type` still verified. A resumed `execute` also refuses an approval that differs from the first journal record, before any further write. Run directories created before this change lack the hash and now fail verification; re-run them. The committed demo report, journal and receipt were regenerated; only the new field and the hashes that depend on it changed.
- `delivery verify` now also checks that the retained `approved-plan.json` and `before-catalog.json` hash to the receipt's plan and before hashes, and that `approval.json`'s plan hash and approver match the receipt and the journal's first approval record. Before this, editing the approver after a successful run still verified. Six new tests cover each check; the 41 existing tests pass, and at that change the committed demo report, journal and receipt regenerated byte-identically.

## 2026-10-06

- Added a runnable synthetic SQL-lineage/environment delivery with exact-plan approval, bounded retries, write-ahead/checkpoint recovery, independent readback, retained failed candidates and hash-chained receipts.
- Expanded the SQLite harness from four to eleven checks, including stable-key value and parent reconciliation. Negative-path harness and delivery/integrity tests pass locally; unknown or computed lineage remains explicit.
- Rewrote the README and architecture/governance/routing documentation around implemented behavior, reviewer navigation, generated proof and explicit source/production boundaries. No live cloud or model adapter is implied.
